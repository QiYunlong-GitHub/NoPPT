# Design Review: Presentation Visual Integrity Bug Fix

**Reviewed design:** `02-design.md`  
**Requirements baseline:** `01-requirements.md`  
**Verdict:** `CHANGES_REQUESTED`

## Findings

1. **HIGH — Hermes draft contract is contradictory and currently wrong.**
   **Where:** `02-design.md`, §8 “Hermes mock contract”; requirements FR-10. The design requires `mode` to be fixed to `auto` and says a successful response may contain only `{ openUrl }`, but its implementation boundary does not specify the controller changes needed to enforce either rule. The actual source contradicts the claimed contract: `packages/server/src/modules/mcp/mcp.controller.ts` defines `mode: z.enum(['auto', 'guided']).optional()` and `prepareOutlineDraft()` returns `draftId`, `openUrl`, `expiresAt`, `mode`, `topic`, `meta`, and `note`. `draft-store.ts` also persists `guided` mode. This is not a harmless compatibility detail: it violates an explicit acceptance criterion and exposes more data than the required tool response.
   **Concrete fix:** Make the contract exact in the design and tests: `mode: z.literal('auto').default('auto')`; reject `guided`; keep the internal draft record if needed but make the tool handler return exactly `{ openUrl: buildOpenUrl(rec) }`. Add a contract test that parses the JSON tool payload and asserts `Object.keys(payload).sort()` equals `['openUrl']`, `mode === 'auto'`, the reference limit is `clamp(3000, 20000, 800 * slideCount)`, the head is retained on truncation, and both `noppt_generate` and promotion spies have zero calls. Specify that key material is read only through `readMcpEnv` and never enters the returned payload or audit artifact.

2. **HIGH — Candidate-only isolation is not designed as an enforceable write boundary.**
   **Where:** `02-design.md`, §§6.2, 6.3, 7, 9; requirements FR-8/FR-9 and Acceptance 15–16. The design names an artifact store and says `runFinalWrite`, `runAutoAudit`, `PresentationService.save`, and audit share an `IntegrityGate`, but it does not define how a run context reaches every write or how an active-path write is rejected. The actual source still writes active files: `final-write.ts` writes `<presentationDir>/presentation.json`; `auto-audit.ts` writes the same file after fixes; `AuditService.persistReport()` writes `<presentationDir>/audit/latest-report.json` and screenshots; `PresentationService.save()` writes active `presentation.json`; the image regeneration loops also write active files. A later implementer can add a candidate service while leaving one of these paths unchanged, which would violate the no-promotion requirement and corrupt the read-only baseline.
   **Concrete fix:** Define an explicit `IntegrityRunContext` required by every generation/audit/fix/save/export entry point, containing `runId`, `writePolicy: 'candidate_only' | 'active'`, `artifactRoot`, `baseManifest`, and `promotionConfirmed`. Make all active writes go through one `ArtifactStore` method that rejects `candidate_only` writes whose path is outside `artifactRoot`; remove direct `join(getPresentationDir(...), 'presentation.json')` writes from final-write, auto-audit, audit persistence, and regeneration loops. For editor/MCP saves, state whether the request is a normal active save or a target candidate save and require an explicit policy; for this run, reject active saves. Add a test that spies on every storage write and fails if any target-original path is touched, including reports, screenshots, logs, assets, and reference attributes.

3. **HIGH — The typed compare and metric contracts do not define the target data model or count semantics.**
   **Where:** `02-design.md`, §1.1 and §2.3; requirements FR-2, FR-3.2–3.4, Acceptance 3, 7–9. `ComparisonItem` is defined with `leftText` and `rightText`, while the requirement describes four compare items with stable identity, order, text, and column ownership (two visible items per column). It is therefore unclear whether four items means four pairs or four total items, and the legacy adapter cannot safely map the target’s four one-sided `keyPoints` into `leftText/rightText` without inventing pairings. Likewise, `MetricItem` requires a non-empty `value`, but the target has four source strings with no separable value/label; the design says to record `needs_review` while also proposing a required `MetricItem`, leaving no legal normalized representation for “preserve the full string, but value is unavailable.”
   **Concrete fix:** Choose and document one schema. For the stated acceptance criteria, use `ComparisonItem { contentId, text, column: 'left'|'right', order, bullet }` and validate exactly four required items with two per column, or explicitly change the requirement mapping to two paired items and show the deterministic legacy conversion. For metrics, use a discriminated union such as `{ kind: 'metric', label, value } | { kind: 'omission', contentId, originalText, reason, status: 'needs_review' }`; never construct an empty `value` or label. Specify the deterministic adapter for the target legacy strings, its issue codes, and the exact contentId/order/column manifest propagated to Deck, HTML, editor, and export.

4. **HIGH — The single-canvas/custom-size transform is not specified sufficiently to be implementable without a second coordinate model.**
   **Where:** `02-design.md`, §§2.1, 2.2, 3.1, 4; requirements FR-4/FR-5 and NFR-2. The design says all generated nodes are 1280×720 logical pixels while custom presentation dimensions are mapped by an “explicit linear transform,” but it never defines that transform, its origin, rounding, clipping behavior, or where it is applied. The actual source has multiple competing semantics: `deckSlideToHtml()` emits `options.width/height` as the root dimensions while node rectangles remain deck coordinates; `presentationToDeck()` and `htmlToDeck()` use presentation width/height directly; `EditorLayout` sizes the canvas to `presentation.width/height`, applies a centered CSS `transform: scale(zoom)`, and the selection/paste code divides by the stored zoom. The design also says to put measurement/profile data in Deck node metadata, but `DeckNodeBase` has no metadata field.
   **Concrete fix:** Define and use a typed `LogicalCanvasTransform` with `logicalRect={1280,720}`, `renderRect`, `scaleX/scaleY` (or explicitly prohibit non-uniform scaling), `offsetX/offsetY`, `logicalToViewport()` and `viewportToLogical()`, plus a rounding/error policy. Apply the same object in canonical HTML, editor pointer/selection/resize/paste, HTML fallback, and PPTX export. State that required nodes are validated before transform and never clamped after it. Add `DeckNode.metadata` or a slide-level `layoutMetrics`/`IntegrityReport` field for measured size, line count, and status; do not require undeclared fields. Include tests for 1280×720 and at least one custom canvas size at all three viewports.

5. **HIGH — `unverified` is not integrated into the existing audit/gate aggregation.**
   **Where:** `02-design.md`, §§5–6.1; requirements FR-1.3, FR-7.2, FR-8.4 and Acceptance 12–13, 20. The design introduces `IntegrityReport.status` values including `unverified` and says Chromium/font unavailability must not pass, but it does not define how that result is represented in the existing public audit types or how the save/export/promotion gate aggregates it. The actual `packages/audit/src/types.ts` only allows engine statuses `passed|warn|fail|error` and overall results `pass|warn|fail`; `VisualAuditEngine` returns `status: 'error'` when Chromium cannot start. Without an explicit mapping, environment absence will either be reported as a product error or disappear behind the existing overall pass calculation.
   **Concrete fix:** Specify the state machine and implement it end to end. Extend the public engine/overall status unions or add a required `verificationStatus` field with `verified|unverified|failed`; map browser/font API absence to `unverified`, structural/content/parity failures to `failed`, and aggregate any required unverified check to overall `unverified`/`needs_review`, never `pass`. Define per-check precedence, including “structural fail + browser unavailable,” and make `IntegrityGate` reject promotion and “overall pass” for either required fail or required unverified. Add tests for absent Chromium, absent `document.fonts`, measurement exceptions, and mixed five-slide results.

6. **HIGH — Font fallback detection is underspecified and the proposed resolution rule is not reliable.**
   **Where:** `02-design.md`, §5; requirements FR-7 and Acceptance 12. The design says “declared family and first fallback are the same” means `resolved`, but computed CSS does not establish the actual font used for each glyph, and CJK text can fall back per glyph even when the CSS family stack is unchanged. It also does not define the node sampling set, requested weight matching, metric-delta baseline/profile, threshold, or the behavior when `document.fonts.check` is present but cannot identify the shaped font. The actual `font-icon-check.ts` only collects the first computed family and font sizes; it records no declared-vs-actual state, weight, line height, or measurement delta.
   **Concrete fix:** Define `FontProfile` per required title/body node and a deterministic observation algorithm: check each declared family/weight with `document.fonts.check`, measure representative text/glyph probes using the declared and fallback profiles, compare DOM/canvas widths and heights against the selected profile, and record `resolved|fallback|unverified|failed` with a reason and threshold. If the browser cannot prove the actual face, return `unverified`, not `resolved`. Specify the reflow trigger and whether a metric delta produces warning, fail, or a new candidate layout; add fixtures for Latin, CJK, mixed text, missing font API, and missing font face.

7. **HIGH — The editor save path does not have a concrete transaction for keeping HTML, Deck, and identities consistent.**
   **Where:** `02-design.md`, §§3.2–3.3, 4, 6.2; requirements FR-2.4, FR-5.4, FR-6 and Acceptance 7, 11, 14. The design proposes `canonicalDomToDeckPatch`, but does not specify how it is invoked from the current editor or how a save updates both representations atomically. The actual `EditorLayout.saveSlideHtml()` serializes only `innerHTML` and calls `updateSlide({ html })`; `PresentationService.save()` only sanitizes HTML and writes it, while MCP edit paths also modify/save HTML directly. No current path applies DOM changes to `slide.deck`, preserves `data-content-id` through sanitization, or rejects deletion/geometry changes before the active write. “Mark manual and use fallback” is not enough because the requirement still demands traceability and an explicit parity/needs-review state.
   **Concrete fix:** Define a single `saveSlideWithIntegrity(slideId, html, deckPatch, runContext)` transaction. Require canonical nodes to carry stable IDs; map text and rect edits by ID; if mapping fails, persist an explicit `source='manual'`, `parity='unverified'`, `geometryFallback=true` result only in the permitted storage target. Run content/geometry/parity checks before commit, return HTTP 422 with `code`, `reportPath`, and unchanged active content for required deletion/out-of-bounds/parity failures, and preserve unsaved UI state. Update `EditorLayout`, the store/API, `PresentationService.save`, and all MCP edit paths to use this transaction, and define the behavior for user-created nodes that have no contentId.

8. **HIGH — The design does not cover every export entry point with the required parity gate and Deck priority.**
   **Where:** `02-design.md`, §3.3 and §9 file boundaries; requirements FR-6.3–6.5 and Acceptance 7, 14. The proposed `presentationToDeckWithIntegrity` is in `packages/web`, but the actual MCP/server export path calls `buildSelfContainedDeck()` in `packages/server/src/modules/mcp/deck-builder.ts`, which sanitizes and exports `slide.html` directly and never reads `slide.deck` or runs parity. The existing web `presentationToDeck()` is also a compatibility wrapper that silently returns a Deck, and its mixed-source `Deck.source` is computed only from `slides.some(s => s.deck)`, so a presentation with both Deck-backed and fallback slides can be mislabeled as entirely `plan`.
   **Concrete fix:** Enumerate every export caller (web PPTX, web HTML, MCP `noppt_export_html`, MCP view, and any server/PPTX path) and route each through one `exportWithIntegrity` adapter. It must select Deck only after parity passes, reject parity/required-geometry failures with a diagnostic result, and permit HTML-only/manual fallback only with explicit `source='html'|'manual'`, `geometryFallback=true`, and `parity='unverified'`. Define a per-slide source for mixed presentations and update all callers so no old compatibility wrapper can silently bypass the gate.

9. **HIGH — Required render/visual_validation/audit/fix evidence has no specified producer wiring or lifecycle.**
   **Where:** `02-design.md`, §§6.3, 7, 10, 11; requirements FR-8 and Acceptance 13, 18. The design lists event fields and introduces `IntegrityEventWriter`, but it does not say which concrete functions emit each event, how one `runId` is created and propagated through generation, repair, preview, editor save, and export, or how an event-write failure changes the gate. The actual audit service persists `latest-report.json` and screenshots under the active presentation directory and the current generation logs use existing AI log calls; `SlideRenderer` has no event writer. Consequently the required five-page, per-phase evidence cannot be inferred from the proposed interfaces alone.
   **Concrete fix:** Add an event matrix with mandatory producers: Deck render/finalize emits `render`; each viewport/browser pass emits `visual_validation`; every integrity-engine execution emits `audit`; every automatic repair emits `fix` before and after revalidation; editor save/export emits their phase event. Pass a required run context to each producer, include all required counts/statuses/artifact paths, write only to the candidate run log, and make missing or failed event persistence produce `unverified`/`needs_review`. Require a post-fix new input hash and new event IDs, not reuse of pre-fix pass results. Add a five-slide test that verifies all required event types and joins them by `(runId, presentationId, slideIndex, phase)`.

10. **MEDIUM — Fallback provenance and geometry-degradation fields are not represented in the declared Deck schema.**
    **Where:** `02-design.md`, §§1.2, 2.1, 3.3; requirements FR-6.4 and Acceptance 14. The design requires historical HTML/manual fallback to carry `source=html`, `geometryFallback=true`, and a parity/validation downgrade, but only proposes `contentManifest` and `layoutProfile` on `DeckSlide`; it does not declare where `source`, `geometryFallback`, or per-slide parity status are stored. The actual core schema has `source` only on the top-level `Deck`, and `DeckSlide` has no such fields. A return-only value from `presentationToDeckWithIntegrity` will be lost by callers that persist or pass only `Deck`.
    **Concrete fix:** Declare a backward-compatible per-slide provenance type, for example `DeckSlide.integrity?: { source: 'plan'|'html'|'manual'; geometryFallback: boolean; parity: 'pass'|'fail'|'unverified'; issues: string[] }`, or require every consumer to carry a typed `ExportResult` instead of a bare Deck. Define serialization compatibility and test that mixed Deck/HTML presentations retain provenance through web export, server export, and PPTX input.

## Verified Assumptions

- The target runtime presentation exists at `packages/server/data/tenants/default/users/default/workspace/presentations/pres_musb7z42_ls8yvjc/` and has five slides. The checked `presentation.json` contains the reported cover title, a single-column HTML representation on the compare slide while its Deck is two-column, four empty metric-description text nodes on the stats slide, three title-only cards on the cards slide, and only the first summary key point in the summary HTML. The target `ai-log.jsonl` does not provide the required `render`, `visual_validation`, `audit`, and `fix` evidence loop.
- `SlidePlan` currently contains weak legacy fields (`keyPoints`, `metricValues`, `showcaseMetrics`) and no typed compare/metric/card/summary item fields. `planToDeck()` currently always returns a Deck, including for a null/empty plan, and `layoutSlideNodes()` catches builder errors and clamps every node with `clampToSlide()`.
- `layout-content.ts` currently lays out compare content by splitting `keyPoints` into halves, cards by `splitTitleBody()`, and summary by `(sp.keyPoints ?? [])[0]`. `layout-advanced.ts` currently creates empty metric values/labels when it falls back from legacy key points, matching the design’s stated defect.
- `DeckNodeBase` currently has no `contentId`, `source`, or metadata field; `DeckSlide` has no content manifest, layout profile, fallback provenance, or per-slide integrity status.
- `deck-to-html.ts` currently renders a fixed-position root with caller-provided width/height and applies `overflow:hidden` to text, shape, table, and chart containers. It does escape text and restrict hyperlinks to `http(s)`/`mailto`.
- `presentationToDeck()` currently prefers a non-empty `slide.deck`, otherwise uses `htmlToDeck()` or an empty slide and never performs a parity gate. `htmlToDeck()` explicitly falls back to approximate vertical stacking when DOM measurement is unavailable.
- `EditorLayout` currently renders the HTML-only `contentRef` inside a canvas sized to presentation dimensions and uses CSS `transform: scale(zoom)`. Selection, paste, and resize code divide viewport measurements by the stored presentation zoom.
- `useZoom()` currently combines presentation dimensions, editor padding, a `0.95` factor, timer retries, and `ResizeObserver`; it does not expose the proposed `ViewportState`/profile contract.
- `font-icon-check.ts` currently records computed font-family names and font sizes plus icon-style heuristics, but no declared/actual family, weight, line-height, font status, or metric delta. `VisualAuditEngine` returns an engine `error` when Chromium cannot start.
- `runFinalWrite()`, `runAutoAudit()`, `AuditService.persistReport()`, and `PresentationService.save()` currently write active presentation/report paths. These are source-level facts, not assumptions from the design.
- `noppt_prepare_outline_draft` currently accepts `guided`, persists it, and returns fields beyond `openUrl`; `referenceTextLimit()` does implement the 800-per-slide calculation with 3000/20000 bounds, subject to environment configuration.

## Unverified/Wrong Assumptions

- The design’s assertion that the current repository already satisfies an auto-only, openUrl-only Hermes draft contract is wrong; the actual controller and draft store allow guided mode and return the full draft payload.
- The design’s statement that browser failure will be represented as `unverified` is not true of the current audit pipeline and is not made mechanically true by the proposed optional `IntegrityReport`; existing public status unions and aggregation still use `error`/`fail`/`pass`.
- The design assumes a typed content contract can safely adapt the target four compare strings into `leftText/rightText` pairs, but it does not define a deterministic pairing/column rule and the stated item-count requirements are ambiguous.
- The design assumes a “logical 1280×720” declaration is enough to unify custom canvas sizes, editor CSS scaling, HTML rendering, HTML fallback, and export. The actual code uses presentation dimensions in several paths, and the design does not define the required transform or metadata fields.
- The design assumes adding `canonicalDomToDeckPatch` will close editor parity, but no current save path invokes such a patch and the design does not define the atomic HTML+Deck transaction or all non-editor save paths.
- The design assumes adding a web export helper will protect exports globally, but server MCP/view export currently uses `buildSelfContainedDeck()` directly and is outside the proposed web file boundary.
- The design assumes an event schema is sufficient evidence. It does not identify producers, run-context propagation, artifact routing, or the failure behavior when event persistence is unavailable.
- The target browser/font availability, actual glyph-level font resolution, and Playwright visual measurements were not verified here because that requires running the browser validation path; those outcomes must remain `unverified` until the candidate test produces evidence.

**Mechanical verdict: CHANGES_REQUESTED (9 HIGH findings and 1 MEDIUM finding).**
