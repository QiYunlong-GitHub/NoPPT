# Design Review — Presentation Visual Integrity Fix

## Verdict

**CHANGES_REQUESTED**. There are 8 HIGH/MEDIUM findings. The design is not ready for implementation until the fixes below are made explicit.

## Findings

1. **HIGH — The proposed `cqw` responsive renderer is incompatible with the current HTML sanitization contract.**
   - **Where:** Design §3.1, especially the `container-type:size`, `container-name:noppt-slide`, and `cqw` requirements.
   - **Problem:** `deck-to-html.ts` is required to emit container-query properties, but the shared allowlist currently contains `aspect-ratio` and ordinary sizing properties only; it does not contain `container-type` or `container-name` (`packages/core/src/security/html-allowlist.ts:148-275`). The generated HTML is sanitized on the existing paths, so the required containing block can be removed. Without the containing block, `cqw` is not relative to the 1280 logical slide root, and the same absolute descendants can scale incorrectly at wide viewports. This directly defeats the narrow/wide validation requirement.
   - **Concrete fix:** Choose one of these explicit implementations: (a) add `container-type` and `container-name` to the shared allowlist and prove both server and web sanitizers preserve them, with a sanitized-output test at 800/1280/1600 widths; or (b) do not use container units and emit a single allowed transform/scale strategy. The design must also specify how `cqw` is detected and marked `unverified` when unsupported.
   - **Evidence:** `packages/core/src/security/html-allowlist.ts:148-275` lists allowed CSS properties and has no `container-type`/`container-name`; `packages/ai/src/agents/html-presentation/deck/deck-to-html.ts:1-18` states the current renderer keeps logical descendants and only makes the root responsive.

2. **HIGH — The empty-manifest parity fix is not wired through the actual audit caller.**
   - **Where:** Design §2.4 and §8.1 item 2.
   - **Problem:** Updating `compareContentCollections` alone cannot close page-1 parity. The content audit only calls it when `planManifest.length > 0 && (deckManifest.length > 0 || htmlManifest.length > 0)` (`packages/audit/src/engines/content-engine/index.ts:184-188`). If both observed manifests are empty, the comparison is skipped and no missing-manifest issue is emitted. The visual validator also returns parity `pass` when `deckRequired.length === 0` (`packages/audit/src/engines/visual-engine/visual-validation.ts:89-99`). The design does not require changing either caller or passing the plan’s required set into visual parity.
   - **Concrete fix:** Define a single comparison entry point that always receives the plan-required manifest and invokes the comparison even when Deck and HTML are both empty. Permit `pass` only when the plan-required set is empty. Add a regression fixture with non-empty plan content and empty Deck/HTML manifests and assert `missing_content` plus `fail`/blocked export.
   - **Evidence:** `packages/audit/src/engines/content-engine/index.ts:184-188`; `packages/audit/src/engines/visual-engine/visual-validation.ts:89-99`.

3. **HIGH — The cover identity plan does not define how the title and three cover items enter the required manifest.**
   - **Where:** Design §2.4 and the invariant in §1.2.
   - **Problem:** The design names IDs (`slide-1-title`, `slide-1-cover-1` …) but does not define a normalized cover-content contract or expected source mapping. In the actual implementation, `layoutCover` creates a title and up to three `keyPoints` text nodes with only roles and no `contentId` (`packages/ai/src/agents/html-presentation/deck/layout-content.ts:24-105`). `collectRequiredContent` currently collects comparisons, metrics, cards, and summary items, but not the title or cover key points (`packages/ai/src/agents/html-presentation/deck/slide-contract.ts:253-262`). Therefore the proposed four-entry manifest cannot be produced deterministically merely by changing `annotateContentNodes`, and a fuzzy fallback could assign the wrong item/order.
   - **Concrete fix:** Specify a cover normalization result containing exactly the title plus the first three required cover source items, with explicit source paths, stable IDs, roles, order, and required status. Make `layoutCover` consume those entries and set IDs directly on nodes; make both Deck and canonical HTML manifests derive from that same list. Define behavior for fewer/more than three cover items and add an exact page-1 fixture assertion.
   - **Evidence:** `packages/ai/src/agents/html-presentation/deck/layout-content.ts:24-105`; `packages/ai/src/agents/html-presentation/deck/slide-contract.ts:253-262`.

4. **HIGH — Strict generation still has an underspecified HTML fallback that can produce a persistable non-pass candidate.**
   - **Where:** Design §2.1, §1.3, and the stated “strict fatal issue returns no persistable Deck” rule.
   - **Problem:** A strict call can still return a Deck with `status: 'needs_review'` for recoverable contract issues, while the design only says fatal issues return no Deck. The current finalizer catches all Deck-construction errors, logs “build deck skipped,” and returns the HTML presentation (`packages/ai/src/agents/html-presentation/stages/finalize.ts:93-115`). The deterministic renderer currently calls bare `planToDeck` without strict mode (`packages/ai/src/agents/html-presentation/stages/render-deck.ts:369-377`). The design does not define how a recoverable `needs_review` result or caught Deck failure is prevented from entering a verified candidate/persistence path.
   - **Concrete fix:** Change production generation to return and persist a typed `PlanToDeckResult`/issue report, and make candidate acceptance require `status === 'pass'` (or explicitly mark the result `legacy_unverified` and block verified save/export). Remove the catch-as-success behavior for candidate production, or make its output an explicitly blocked candidate with stable issue codes. Add a test proving `needs_review` cannot be saved or exported as verified.
   - **Evidence:** `packages/ai/src/agents/html-presentation/deck/plan-to-deck.ts:297-320`; `packages/ai/src/agents/html-presentation/stages/finalize.ts:93-115`; `packages/ai/src/agents/html-presentation/stages/render-deck.ts:369-377`.

5. **HIGH — The design does not prevent direct PPTX/export callers from bypassing the integrity boundary.**
   - **Where:** Design §7.1, §7.2, and §12 claim that `deck-to-pptx.ts` cannot bypass provenance.
   - **Problem:** The current export path calls `presentationToDeck` directly from `ExportModal` (`packages/web/src/components/ExportModal.tsx:495-510`). `presentationToDeck` intentionally returns HTML fallback slides with `source: 'html'`, `parity: 'needs_review'`, and `geometryFallback: true` (`packages/web/src/export/presentation-to-deck.ts:116-151`). However, `buildPptx` blocks only slides with `source === 'plan'` and non-pass parity (`packages/web/src/export/pptx/deck-to-pptx.ts:191-199`), so an HTML fallback can reach PPTX export. Saying callers “use `exportWithIntegrity`” is not enough while the public low-level export API remains permissive.
   - **Concrete fix:** Define `exportWithIntegrity` as the only verified export API and update every UI/server/MCP/PPTX caller to use it. Also make `buildPptx` reject any Deck or slide whose integrity/parity/provenance is not verified, regardless of `source`; expose a separately named legacy/manual export that returns an explicitly unverified result if compatibility requires it. Add a direct-call test for HTML-only fallback and missing-manifest Decks.
   - **Evidence:** `packages/web/src/components/ExportModal.tsx:495-510`; `packages/web/src/export/presentation-to-deck.ts:116-171`; `packages/web/src/export/pptx/deck-to-pptx.ts:191-199`.

6. **HIGH — The shared integrity context and gate API are incomplete and do not carry the state the design later requires.**
   - **Where:** Design §1.1, §1.3, §7.1, and §9.
   - **Problem:** `IntegrityRunContext` contains `baseHash` and `activeWriteConfirmed`, but no `baseUpdatedAt`, immutable snapshot/manifest reference, evidence report type, or explicit promotion confirmation field. Later rules require matching `baseHash`/`updatedAt`, artifact evidence, and a verified report. The design also references `assertIntegrityEvidenceForSave(report, { requireVerified: true })` without defining `report`, its required-page/cell schema, issue-code result type, or the adapter between that API and the existing server store. The actual server service has its own `IntegrityCheckResult`, `PromotionOptions`, `baseUpdatedAt`, and explicit promotion confirmation (`packages/server/src/modules/presentation/presentation-integrity.service.ts:1-66`), so the proposed core contract is not yet the source of truth.
   - **Concrete fix:** Define exact shared types and signatures before routing callers: `IntegrityEvidenceReport` (run/presentation IDs, snapshot hash and updatedAt, required matrix cells, per-cell statuses, font/parity/content results, artifact paths), `assertIntegrityEvidenceForSave(report, policy)`, and `IntegrityOperationResult`. Include `baseUpdatedAt`, snapshot/manifest path, `activeWriteConfirmed`, and a distinct `promotionConfirmed` where applicable. Specify how server `PromotionOptions` and store state map to those core types, and reject missing context/report before any write.
   - **Evidence:** Design §1.1 only defines `baseHash?: string`; design §1.3 references an undefined report contract; `packages/server/src/modules/presentation/presentation-integrity.service.ts:1-66` defines a separate lifecycle/check model.

7. **MEDIUM — The validation result schema does not satisfy the required per-page/per-viewport evidence matrix.**
   - **Where:** Design §4.2 and §10 validation plan.
   - **Problem:** The prose requires each page/viewport cell to carry clipping, overflow, overlap, empty-node, parity, font, screenshot path, and final status, but the described/current shape is slide-level `screenshotPaths` and `metrics`, while resize metrics are only `Pick<LayoutMetrics, 'viewport' | 'requiredClipped' | 'emptyRequiredNodes' | 'horizontalOverflow' | 'titleOverlap'>` (`packages/audit/src/engines/visual-engine/visual-validation.ts:43-60`). Resize cells therefore omit parity/font/resource state and screenshot paths, and there is no schema rule that the supplied `resizeSequence` is exactly the required five-state forward/reverse sequence. This makes “complete matrix” non-machine-verifiable.
   - **Concrete fix:** Define `VisualValidationCell` with viewport, profile, resize step/direction, all required metrics, parity, font evidence, resource status, screenshot path, evaluator version, error code, and final status. Store cells for all three initial viewports and all five resize states, validate the exact required sequence by default, reject incomplete/custom sequences for the release harness, and define screenshot requirements for resize cells.
   - **Evidence:** `packages/audit/src/engines/visual-engine/visual-validation.ts:43-60, 167-169, 230-248`.

8. **MEDIUM — The font/resource evidence contract is richer in prose than at the validation gate.**
   - **Where:** Design §6, §4.2, and §8.
   - **Problem:** The design requires declared stack, requested/resolved weight, deltas, representative node/role, and missing-API reasons, but `VisualFontEvidence` currently exposes only status, two family strings, `fallbackUsed`, and readiness (`packages/audit/src/engines/visual-engine/visual-validation.ts:25-34`). The proposed design does not define the mapping from `FontValidationResult` to every matrix cell or the blocking rule for image/resource failures. The current `hasBlockingMetric` checks failed fonts but not image readiness (`visual-validation.ts:130-131`), while the requirement says missing required evidence must block verified release.
   - **Concrete fix:** Extend the per-cell font evidence with profile/stack, requested and resolved weights, metric deltas, affected IDs/roles, and API availability/reason. Define `resource_failed`, `resource_unverified`, fallback-with-layout-delta, and missing-API aggregation precedence; require those statuses to block verified save/export when the affected node is required. Add resolved/fallback/failed/missing-API and required-image failure fixtures.
   - **Evidence:** `packages/audit/src/engines/visual-engine/visual-validation.ts:25-34, 118-131`; `packages/audit/src/engines/visual-engine/font-icon-check.ts:40-72` shows the richer classifier exists separately but is not the shape consumed by visual validation.

9. **NIT — The prescribed focused test command contains paths not present in the workspace source tree.**
   - **Where:** Design §10 command block.
   - **Problem:** The command names `src/engines/visual-engine/__tests__/presentation-visual-integrity.exploration.test.ts` and `src/engine/integrity-evidence.test.ts`; the workspace source has `presentation-visual-integrity.exploration.ts` and `integrity-evidence.ts`, but no matching `.test.ts` at those paths. A command that silently resolves only through package `node_modules` or fails to find a file cannot be the required validation record.
   - **Concrete fix:** Add the named tests in the workspace or correct the command to the actual test files, and make the validation report record the exact resolved paths and exit status.
   - **Evidence:** Workspace search found `packages/audit/src/engines/visual-engine/__tests__/presentation-visual-integrity.exploration.ts` and `packages/audit/src/engine/integrity-evidence.ts`; no corresponding workspace `.test.ts` paths were found.

## Verified Assumptions

- `planToDeck` defaults to `validationMode: 'legacy'`, and both production generation callers currently omit strict validation: `packages/ai/src/agents/html-presentation/deck/plan-to-deck.ts:297-320`, `stages/finalize.ts:93-115`, and `stages/render-deck.ts:369-377`.
- The visual harness currently sends TypeScript function callbacks to `page.evaluate`; `SlideRenderer.waitForFonts`, `waitForResources`, and `collectLayoutMetrics` do so at `packages/audit/src/engines/visual-engine/slide-renderer.ts:191-341`. `visual-validation.ts:118-128` currently hard-codes `fallbackUsed: false`.
- The current cover renderer creates a title and up to three `keyPoints` nodes with semantic roles but no stable IDs, and the current required-content collector excludes the title and omission entries: `packages/ai/src/agents/html-presentation/deck/layout-content.ts:24-105`; `slide-contract.ts:253-269`.
- `PresentationIntegrityService` already provides candidate writing, preview creation, run state, hash snapshots, and promotion/rollback primitives: `packages/server/src/modules/presentation/presentation-integrity.service.ts:20-66, 297-352, 603-647`.
- Direct active persistence remains in `PresentationService.save` and in AI post-processing fallbacks, while MCP edit handlers call `presentationService.save`: `packages/server/src/modules/presentation/presentation.service.ts:108-120`; `packages/server/src/modules/ai/postprocess/final-write.ts:349-354`; `auto-audit.ts:105-113`; `packages/server/src/modules/mcp/mcp.controller.ts:676-741`.
- HTML-only export is explicitly downgraded by `presentationToDeck`, but the low-level PPTX guard currently only rejects non-pass plan-backed slides: `packages/web/src/export/presentation-to-deck.ts:116-171`; `packages/web/src/export/pptx/deck-to-pptx.ts:191-199`.
- The current editor uses a scaled stage and a separately transformed logical canvas, with dimensions derived from presentation metadata rather than an invariant 1280×720 canvas: `packages/web/src/layouts/EditorLayout.tsx:1253-1338`.

## Unverified/Wrong Assumptions

- **Wrong/incomplete:** The design’s §2.4 current-state claim that `compareContentCollections` itself passes a non-empty expected collection when observed manifests are empty is not true for the inspected function: it emits identity/missing issues. The actual gap is the caller in `content-engine/index.ts` skipping the comparison when both observed collections are empty, plus visual validation lacking the plan manifest.
- **Unverified:** The prior Task 13 browser failures and Task 16 `__name` error are design inputs, not independently reproduced in this read-only review. No browser harness or live service was run here; those claims must remain evidence-backed in the final validation report.
- **Unverified:** The target presentation’s exact page-1 source IDs and page-3 metric 3–4 source strings were not specified in the design or verified from protected runtime inputs. The implementation must not invent expected IDs/values; it needs an isolated fixture or read-only hash-preserving extraction of the target plan.
- **Wrong as an implementation guarantee:** Saying that `exportWithIntegrity` will be used by callers does not by itself prevent direct use of the existing public `presentationToDeck`/`buildPptx` APIs. The low-level guard and all current call sites must be changed or the bypass remains.
- **Unverified:** The design’s statement that CSS container units are supported by the validation baseline does not establish that the project’s server/web sanitizers preserve the required container properties; the current shared allowlist disproves preservation unless it is changed and tested.
